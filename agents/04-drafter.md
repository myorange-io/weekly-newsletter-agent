# 4. 초안가

**우리 조직 말투로** 초안을 씁니다.

## 판단 기준

### 규칙은 프롬프트 안에 쓰지 않는다

이게 핵심입니다. 문체 규칙을 프롬프트 본문에 섞어 쓰면, 규칙 하나 고칠 때마다 프롬프트 전체가 흔들립니다.

→ 규칙은 **별도 파일**에 두고 프롬프트 **앞에 붙입니다**(prefix). 본문은 건드리지 않습니다.

```
[규칙 파일 내용]      ← 여기만 갈아끼운다
[예시 5~10개]         ← 여기만 갈아끼운다
---
[고정된 작업 지시]     ← 절대 안 건드린다
[이번 건의 원문]
```

규칙 파일은 사람이 손으로 써도 되고, 사람이 고친 전후 쌍에서 뽑아낼 수도 있습니다 → [부록: 문체 학습](../appendix/voice-training.md)

### 예시가 규칙보다 강하다

"간결하게 쓰세요" 같은 서술보다 **전후 예시 한 쌍**이 훨씬 잘 먹힙니다. 규칙 서술과 예시를 둘 다 주되, 예시를 아끼지 마세요.

### 형식은 코드로 강제한다

말투는 LLM에 맡기되, **기계가 판정할 수 있는 규칙은 코드로 처리**합니다. LLM에 맡기면 열 번 중 한두 번은 틀립니다.

오렌지레터의 예:
- 문장 끝 마침표 제거 (중간 마침표는 유지)
- 느낌표 전부 제거 (인용문 안은 예외)
- 정해진 구분자 형식 맞추기

이런 건 프롬프트에 쓰고 **동시에** 후처리로 한 번 더 거릅니다.

### 강조는 나중에, 따로

핵심어 굵게 처리 같은 건 초안이 확정된 뒤 별도 단계로 겁니다. 초안 작성과 함께 시키면 문장 자체가 강조를 의식해서 이상해집니다.

## 입력 / 출력

**입력**: 분류가의 출력 + 규칙 파일 + 예시

**출력**
```
초안: <문체 규칙이 적용된 결과물>
적용한 규칙: <어떤 규칙이 걸렸는지>
확신이 없는 부분: <있으면>
```

## 하지 않는 일

**자기 초안을 검수하지 않습니다.** 검수는 [사실 검증관](05-fact-checker.md)과 [비평가](06-critic.md)가 별도 호출로 합니다.
같은 대화에서 이어 물으면 자기 문장을 방어합니다.

## 갈아끼울 자리

규칙 파일과 예시. 이게 조직마다 완전히 다른 유일한 부분입니다. 나머지 구조(prefix 주입 · 코드 후처리 · 강조 분리)는 그대로 씁니다.

## 실측

최근 한 달 512건 초안 생성. 규칙 파일은 분기에 한 번 갱신합니다.
